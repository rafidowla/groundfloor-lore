# Lore v3.18.0

> [!WARNING]
> **This release is affected by a defect fixed in 3.18.2 — upgrade if you
> embed Lore in your own process.** An embedding application can finish all
> its work, close every Lore instance cleanly, and then never exit: a
> background writer re-opened a database that had already been closed, and
> the re-opened engine held the process alive. There is no error and nothing
> shows in Node's own diagnostics, so a passing test suite can still hang
> afterwards. The standalone daemon is not affected. See
> [v3.18.2](v3.18.2.md).

## Highlights

This release is a correctness and hardening pass following a security and
data-integrity audit. The headline fixes close three genuine data-loss and
data-integrity risks: a race condition that could leave a restored graph
empty, a filter bug that could let a bulk delete or update silently wipe an
entire table, and a class of writes that bypassed the per-record write lock.
Alongside those, this release tightens schema validation, standardizes error
handling for malformed requests, reduces what an unauthenticated caller can
see from the health endpoint, and completes the removal of an older graph
engine's naming from error codes and internal identifiers. None of this
changes how you use Lore day to day, but a few response shapes and error
codes did change — see "Breaking or behaviour changes" below before you
upgrade.

## What's fixed

### Data integrity

- **Restore/backup race condition.** Under specific timing, a restore could
  finish reporting success while the restored graph was actually empty,
  because the backend was still flushing to disk after being told to close.
  Backups and restores now wait for the store to fully settle, and a restore
  re-opens and verifies the restored data against the archive before
  reporting success.
- **Filter guard that could wipe a table.** Certain filter shapes (including
  a literal empty filter combined with `all: true`, and some negated
  filters) could match every row in a table without the caller intending a
  full-table operation. Deletes and updates now run a same-transaction
  row-count check and refuse a filter that matches every row on a table with
  more than one row, unless the caller explicitly passes `all: true`.
- **Writes bypassing the record lock.** A background cleanup path
  (expired/ephemeral node pruning) was deleting records without going
  through the same per-record write lock, audit trail, and tombstone
  bookkeeping as every other delete path. It now does.
- Every node delete, update, and edge write now consistently records the
  same lock, audit-log, and recovery bookkeeping that node writes already
  had — edges previously had none of this.

### Security

- **Unauthenticated health endpoint exposure.** An unauthenticated request
  to the health endpoint previously returned detailed internal state
  (storage location, per-workspace counts, background queue depth, rate-
  limit configuration). It now returns only a minimal "is it alive" response
  unless the caller presents a valid access token.
- Every HTTP response now carries baseline browser security headers
  (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
  `Cache-Control: no-store`) and a strict default Content-Security-Policy.
- Continuous integration now runs a dependency vulnerability scan on every
  build and fails on any new high/critical finding, with two already-
  reviewed exceptions tracked explicitly (see "Known limitations").

### API consistency

- Schema creation now validates the request body up front and returns a
  clear `400` error naming the accepted field types, instead of silently
  accepting an invalid schema that would then fail every future insert with
  a confusing error.
- Every API route now returns a consistent `400` error for a malformed or
  truncated request body, instead of an opaque `500` server error.
- A workspace still configured to use the older, removed graph engine now
  gets an honest, clearly-labeled error instead of a generic server error.
- The sync-status reporting endpoint now reports the graph engine a
  workspace is actually running, instead of a hardcoded value.

### CLI

- `lore restore` now checks that an archive's recorded workspace name
  matches the target you're restoring into, and refuses on a mismatch
  unless you pass `--allow-name-mismatch`. This guards against restoring
  the wrong backup into the wrong place.
- `lore backup` and `lore restore` refuse to run while a running Lore
  instance still holds the data store open, closing a window where a
  backup or restore could race a live process.

### Tests and CI

- The automated test suite gained new coverage for the write-lock, filter-
  guard, and restore-verification fixes above, so these classes of bug are
  now caught automatically going forward.
- A drift-detection check now runs in CI to make sure identifiers and
  documentation for the removed legacy graph engine can't silently creep
  back into the codebase.

## Breaking or behaviour changes

- An error code used only when a workspace is explicitly configured for the
  now-removed legacy graph engine has been renamed; that same condition is
  now also reported as HTTP `501` instead of a generic server error. This
  only affects workspaces with that legacy configuration — it does not
  affect a default or normally-configured workspace.
- Creating a collection with an invalid schema now correctly fails with a
  `400` error instead of appearing to succeed and failing later on every
  insert.
- `all: true` is now required (and honoured) to delete or update every row
  in a table via a literal empty filter, matching how every other
  "matches everything" filter already worked.
- An unauthenticated request to the health endpoint gets less detail than
  before. If you have any automation or monitoring that reads the full
  health response without an access token, it will need to start sending
  one.
- A malformed request body now returns `400` instead of `500` across the
  board — if anything in your integration specifically checked for `500` on
  bad input, update it to expect `400`.

## Known limitations

- Two dependency vulnerabilities remain open and tracked, both verified as
  not exploitable in Lore's own usage: one in a PDF-processing library
  (fix requires a major version upgrade, planned as routine hygiene) and
  one in a ZIP-extraction step used only during package installation
  (fix is blocked on an upstream release). Both are documented in detail,
  including the reachability analysis behind each decision, in the
  repository's security advisories reference.
- Backups are not a fully quiesced snapshot: Lore refuses to back up or
  restore while a running instance holds the data store, but does not (yet)
  pause in-flight writes on a store it doesn't control. For the cleanest
  backup, run it while the workspace is idle.
- A dedicated health-check and monitoring strategy for cloud/remote
  deployments is still being designed; the current health-endpoint
  behaviour targets local, single-machine use.
