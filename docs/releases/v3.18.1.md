# Lore v3.18.1

> [!WARNING]
> **This release is affected by a defect fixed in 3.18.2 — upgrade if you
> embed Lore in your own process.** An embedding application can finish all
> its work, close every Lore instance cleanly, and then never exit: a
> background writer re-opened a database that had already been closed, and
> the re-opened engine held the process alive. There is no error and nothing
> shows in Node's own diagnostics, so a passing test suite can still hang
> afterwards. The standalone daemon is not affected. See
> [v3.18.2](v3.18.2.md).

## Highlights

This is a small patch release. It closes a data-safety gap in boot-time
cleanup of expired ephemeral records, restores a default result-size cap on
two analytical query operations so a high-cardinality field can't produce an
unbounded response, and includes two internal code-organization cleanups
with no behavior change. There are no API removals in this release.

## What's fixed

- **Boot-time ephemeral cleanup now fully audited.** When the daemon starts
  up and clears out expired temporary records, that cleanup now goes
  through the same record lock, change log, and recovery bookkeeping as
  every other delete in Lore. Previously it bypassed that bookkeeping,
  which could leave a gap in the audit trail for those specific deletes.
- **`groupBy` and `distinct` no longer return unbounded results.** A query
  grouping or listing distinct values on a field with many unique values
  (an ID, a hash, a timestamp) previously returned one row per value with
  no limit. Both operations now default to a 10,000-result cap, and
  requests that ask for more than the cap get a clamped, clearly-marked
  response instead of being refused outright.
- Two internal cleanups with no user-visible effect: a large routing file
  was split along its natural seam to stay under the project's file-size
  limit, and a circular internal import between two modules was removed.

## Behaviour changes

- A new optional setting, `LORE_ANALYTICAL_GROUP_LIMIT` (default `10000`),
  controls the cap described above. Most installations don't need to touch
  it. If a query previously relied on getting back more than 10,000 groups
  or distinct values with no limit specified, it will now get 10,000 back
  with an indicator that the result was capped; passing a higher limit
  explicitly clamps to the cap rather than failing.
- If anything watches Lore's internal change/outbox activity (for example,
  a connected embedding pipeline), it may now see activity from the
  boot-time cleanup described above that it did not see before. This is
  expected — it's the same bookkeeping every other delete already
  produces, now applied consistently.
- No endpoints, tools, or fields were removed in this release.

## Known limitations

- Two dependency vulnerabilities remain open and tracked, both verified as
  not exploitable in Lore's own usage: one in a PDF-processing library
  (fix requires a major version upgrade, planned as routine hygiene) and
  one in a ZIP-extraction step used only during package installation
  (fix is blocked on an upstream release). Both are documented in detail,
  including the reachability analysis behind each decision, in the
  repository's security advisories reference.
- Backups are not a fully quiesced snapshot: Lore refuses to back up or
  restore while a running instance holds the data store, but does not (yet)
  pause in-flight writes on a store it doesn't control. For the cleanest
  backup, run it while the workspace is idle.
