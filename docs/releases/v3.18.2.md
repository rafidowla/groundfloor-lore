## Highlights

**If you embed Lore in your own process, upgrade from 3.18.0 or 3.18.1.**
On those two releases an embedding application could finish all its work,
close every Lore instance cleanly, and then never exit — the process just
sat there. This release fixes that, plus a second bug of the same kind that
affects the daemon, and three smaller cleanup gaps found alongside them.

There are no API changes and no removals. Upgrading is a drop-in replacement.

## What's fixed

### An embedding application could never exit (regression in 3.18.0)

**Who it affects:** anyone running Lore in-process (Atlas, MIRA, or any
application using `createLore`). The standalone daemon is not affected —
it holds its own process open anyway, which is why this reached a release
unnoticed.

**What you saw:** all work completes, every `close()` returns, every test
passes — and the process hangs forever with no error. In a test runner it
looked like a timeout; run on its own, the terminal just sat there.

**Why it happened:** 3.18.0 restored a background writer that records when
records were last read (used by retention policy). That writer opened the
database if it wasn't already open. It is driven by a repeating timer that
nothing ever stopped, so it kept running after a workspace had been closed —
and re-opened the database from the background. That re-opened database had
no owner, was never closed, and kept the process alive.

**Why it was hard to find:** nothing showed up in the usual places. Node's
own diagnostics reported an idle, empty process. Only `lsof` revealed the
truth: open database files belonging to workspaces that had already been
closed.

**The fix:** the background writer now only records against a database that
is already open, and never opens one. Shutdown now stops these writers
before closing anything, so the pending records still get written rather
than dropped.

### The daily retention sweep could re-open closed databases (daemon)

The same class of bug, found by auditing every repeating background task in
the codebase. The daily retention sweep's timer handle was created inside a
callback and never returned, which made it **impossible to cancel** once
started. The sweep re-opens every workspace it examines.

This never affected embedding applications (they never start it) and never
caused a hang. It affects the daemon, where shutdown also runs on a
workspace switch and on `daemon/restart` — after which the daemon keeps
going. A sweep firing afterwards would re-open the databases that had just
been closed, and could leave two live handles on the same directory.

The sweep can now be cancelled, and shutdown cancels it.

### Three cleanup gaps closed

None of these caused the hang; all three leaked resources on shutdown.

- **A background queue's idle timer no longer keeps a host application
  alive.** Any shutdown path that didn't reach that queue's stop step held
  the host process open indefinitely — including a host that deliberately
  abandons its own shutdown when a write is stuck.
- **Per-workspace search stores are now released on shutdown.** The function
  to release them existed and was documented as running at shutdown, but
  nothing called it, so every workspace touched leaked a handle for the life
  of the process.
- **Five internal SQLite files are now closed on shutdown** in local and
  embedded mode. They were only being closed on the cloud startup path, so
  every other shutdown left their file handles open.

## Upgrading

Drop-in. No configuration changes, no data migration, no API changes.

Embedding applications should re-vendor the tarball and re-run their own
suites — the symptom this fixes is invisible to assertions, so a suite that
passed on 3.18.1 could still have been hanging afterwards.

## Verification

- Lore's full test suite is green.
- Every test in the reporting consumer's suite that embeds Lore passes with
  no hangs (38 of 38). The test that originally hung indefinitely now
  completes in the same time it took on 3.17.0.
- New regression tests cover each fix, and each was confirmed to fail when
  its fix is reverted.
