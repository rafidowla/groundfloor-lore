# Link eval C1: related[] cap and hub exclusion (2026-10-24)

Question: with link ordering ON (the new default), how much do a per-hit neighbour cap and a hub-degree drop improve the related[] list, and do they leave the primary hits alone?

Setup: SQLite graph + vector, real embedder (Xenova/multilingual-e5-small, q8, 384 dims, local ONNX), 10000 code rows (80 knowledge nodes, 300 notes), depth 1, search mode hybrid, max 10, questions questions.json,questions-heldout.json (67 questions x terse + chatty = 134 recall calls per arm). Links from link-on-arrival (minSim 0.80, k 5), the same cached fixture as the B4 links-on arms. Arms differ only in createLore({ recallLinkOrdering, recallRelated }). Same seed and corpus in every arm; one run per arm (the pipeline is deterministic).

Arms: **base** (ordering on, cap off, hub degree > off); **cap2** (ordering on, cap 2, hub degree > off); **cap3** (ordering on, cap 3, hub degree > off); **hub15** (ordering on, cap off, hub degree > 15); **hub20** (ordering on, cap off, hub degree > 20); **hub30** (ordering on, cap off, hub degree > 30); **cap2+hub20** (ordering on, cap 2, hub degree > 20); **cap3+hub20** (ordering on, cap 3, hub degree > 20); **cap3+hub15** (ordering on, cap 3, hub degree > 15).

Grades (lib/linkMetrics.mjs): 3 near-duplicate partner, 2 same component and both curated knowledge, 1 same component (note or code row), 0 unrelated. "Relevant" is grade >= 1, "strong" >= 2.

## What the numbers say

- Primary hits: all 9 arms return the same top-10 as the links-off run in all 134 lists. Neither trim touches the primary list, by construction and by measurement.
- Hub exclusion is the clear win. Dropping neighbours with link degree above 15 or 20 removes every hub node from related[] (111 of 134 lists had one), lifts the first neighbour from 65.1% to 68.3% relevant (24.6% to 26.8% strong), and lifts whole-list precision@10 from 39.8% to 42.0-42.2%. Cost: 3 of 126 lists lose all neighbours of the expected answer (those answers are themselves above the degree limit). A limit of 30 is above the fixture hubs (degree 23: 5 links plus 18 explicit relates_to edges) and does nothing. 15 and 20 behave almost the same here because few code rows fall between them.
- The per-hit cap trims noise but also trims real neighbours. Cap 2 halves the list (40.6 to 18.5 items), cuts noise slots from 73.6% to 67.5% and lifts the hit-relative precision from 68.3% to 77.8%, but the share of lists where the expected answer keeps any strong neighbour falls from 54.0% to 42.9%. Cap 3 loses less (52.4%) and gains less. The cap does not change the first neighbour (it is applied after ordering), so first-neighbour numbers do not move except where it empties a later slot.
- Cap plus hub: cap 3 with hub 20 gives the best balance on the answer-relative view (precision@10 40.1%, strong ceiling 53.7%, noise 67.9%, 25 items per list) and a 79.5%/78.4% hit-relative precision. Cap 2 plus hub 20 is the tidiest list (18 items) but gives up the most real neighbours.
- Latency: all arms within noise of baseline (p50 32-54 ms); the degree reads are memoised per recall and bounded, with no measurable cost here. p95 jitter (68-160 ms) is run noise, not a trend.

## Recommendation (defaults stay OFF in code)

- Hub exclusion: recommend turning on at degree 20 for hosts with link-on-arrival (LORE_RECALL_RELATED_MAX_DEGREE=20). Reason: it is the only trim that improves every answer-relative metric and removes a whole class of noise, for a small ceiling cost. The number is fixture-specific (hubs here are degree 23 against p90 13 for ordinary rows). Treat 20 as a starting point and check the degree distribution of the real workspace before fixing it; a limit near the p99 of link-degree is the form to keep in mind.
- Per-hit cap: recommend NOT defaulting it. If a host wants shorter lists, use 3, not 2: cap 2 costs about 11 points of strong-neighbour coverage for the answer. The cap's benefit is list length and per-hit tidiness, not first-neighbour quality.
- Why not default now: one synthetic corpus, one embedder, SQLite only. Rafi's call whether to flip hub exclusion in a later release once checked on a real workspace.

## Limits

- Synthetic corpus: the component name is in the text the embedder reads, so similarity and ground truth agree more than on real notes; precision leans optimistic.
- 97% of links are code-to-code between near-identical generated rows. The two hub nodes (`fx-hub-*`) have link degree 5 plus 18 explicit `relates_to` edges each. Real hubs (a glossary, an index note) are likelier to have hundreds of links, so absolute thresholds here do not transfer; the degree distribution is in link-eval-2026-10-24.md.
- Hubs are graded 0 against everything, so removing them always looks like a gain. A hub that a human would call loosely relevant is counted as noise.
- Fixture degree: mean 8.4, p50 7, p90 13, max 65 (links only; the hubs add explicit edges).
- One embedder, one corpus, SQLite only; Postgres runs the same code path but was not measured.
