# recall-eval — shared harness for D1 (calibration/abstention) and D3 (rank stability)

This is the D0 deliverable: a deterministic, offline eval harness that D1 and
D3 both build on, so neither has to invent its own fixture or scoring code
and both measure against the exact same corpus.

## What it builds

A synthetic "Riverstone" workspace (a fictional job-orchestration platform,
so there's zero chance of real-corpus contamination):

- **80 curated knowledge nodes** (`lib/anchors.mjs`, 24 hand-authored anchors
  with a terse and a chatty phrasing of the question that should retrieve
  them, `lib/corpus.mjs`'s `buildFillerKnowledge` for the remaining filler,
  `buildNearDuplicates` for 6 near-duplicate pairs) across
  decision/convention/architecture/bug_pattern.
- **300 chatty notes** (`buildChatNotes`) — realistic noise.
- **Code-ish rows**, default 10,000, `--code-rows 100000` for the larger
  fixture — synthetic source-adjacent text, not real code.
- **2 hub nodes** with 18 edges each (36 total) for D4-adjacent context; not
  otherwise used by D1/D3 scoring.

Everything is generated by a seeded PRNG (`lib/rng.mjs`, mulberry32 +
FNV-1a string seeding, fixed seed `riverstone-fixture-v1`), so content and
ids are byte-identical across runs. This matters because `questions.json`
hardcodes expected node ids against the anchors — if you change
`lib/anchors.mjs` or `lib/corpus.mjs`'s shape, regenerate with
`node scripts/diagnostics/recall-eval/genQuestions.mjs` before relying on
the harness again.

## Question sets

- **`questions.json`** — 24 questions, one per anchor, each with a `terse`
  and a `chatty` phrasing and an `expectedIds: [anchorId]`.
- **`gibberish.json`** — 60 queries built from an unrelated vocabulary
  (cooking/mythology/astronomy/textiles/geology/instruments word bank),
  mechanically verified at generation time to have **zero token overlap**
  with the corpus vocabulary (knowledge + notes + code-row sample + the
  question text itself). Don't hand-edit these without re-running the
  overlap check in `genQuestions.mjs` — plain English glue words ("the",
  "into", "for") can't be used in the gibberish templates because ordinary
  prose always contains them, which is why the generator only combines raw
  content words.

- **`identifiers.json`** — 20 queries naming something that IS stored (a
  unique `fixture symbol #N` marker or a code row's file/symbol), each with
  `expectedIds`. Run by default (D3's `--identifiers PATH`; D1's
  `--identifiers-file` is an alias; `--skip-identifiers` turns it off); scored
  rank1/hit@3/found@10/MRR plus abstained/rescued counts. This is the population
  D1's exact-identifier rescue exists for. Shared with D3.
- **`identifiers-absent.json`** — 12 identifier-shaped queries naming nothing
  stored at `--code-rows <= 10000` (`#999999`, `compactGrimoire`, …). Pass
  with `--absent-identifiers-file`; reported like distractors (no pass bar);
  the rescue must never fire on these.

## Running it

```bash
node scripts/diagnostics/recall-eval/runner.mjs \
  --engine sqlite --embedder real --code-rows 10000 --depth 0 \
  --search-mode hybrid --out baseline/sqlite-real-10k.json
```

Flags:
- `--engine sqlite|surreal-lance` — graph+vector engine pair (`sqlite` is
  the 3.21 default for new workspaces; `surreal-lance` is the legacy pair).
  Sets `LORE_DEFAULT_GRAPH_ENGINE`/`LORE_DEFAULT_VECTOR_ENGINE` for fixture
  build.
- `--embedder real|fake` — `real` uses the local ONNX model
  (`Xenova/multilingual-e5-small`) via Lore's own embedding provider
  selection; it **refuses to run if the model isn't already cached** rather
  than triggering a download (see "Embedder caching" below). `fake` injects
  a deterministic 64-dim char-hash `EmbeddingProvider`
  (`lib/fakeEmbeddingProvider.mjs`) for fast, offline CI iteration —
  **never use `fake` for a number that's meant to represent real retrieval
  quality**; it has no semantic structure and both D1's calibration curve
  and D3's score-compression claim are properties of the real embedding
  space.
- `--code-rows N` — default 10000; pass 100000 for the larger fixture size
  mentioned in the original task spec, budget permitting.
- `--depth N` — graph traversal depth passed to `lore.recall()`; **default
  0, deliberately**. `recall()`'s own default is 1, but depth>0 lets D4's
  traversal-splice issue leak into these numbers (an edge-hop can pull in
  an unrelated node and shift rank/score in a way that has nothing to do
  with calibration or stability). This mirrors the same `depth:0` workaround
  Atlas's own PR #30 already uses for the same reason. If D4 needs
  depth-sensitive numbers from this harness, use `--depth 1` explicitly and
  say so in the output — don't change the default.
- `--search-mode hybrid|semantic|keyword` — passed through to `recall()`.
- `--max N` / `--wide-max N` — primary result window (default 10) and the
  wider window used for the prefix-stability check (default 50).
- `--cache-root PATH` — where built fixtures are cached; omit for a fresh
  `mkdtemp` under the OS tmp dir. Fixtures are cached by a hash of
  `(seed, corpus version, graph engine, vector engine, code-row count,
  embedder)`, so re-running with the same shape reuses the build.
- `--force` — rebuild the fixture even if a cache hit exists.
- `--with-queries` — also run each real question's multi-phrasing
  variant (`recall(terse, { queries: [chatty] })`) and report its
  hit@1/hit@3/MRR — the design doc's "queries[] variant" row (same variant
  shape as D1's runner flag of the same name).
- `--out PATH` — JSON report path; a sibling `PATH` with `.md` instead of
  `.json` is also written, and the markdown is printed to stdout.

The script self-re-execs once under `node --import tsx` so it can
`import()` Lore's TypeScript source directly (no dist build required) —
this is the same pattern `scripts/diagnostics/e2e-10-workspace.mjs` uses.

## Embedder caching

`lib/embedCacheCheck.mjs` checks whether
`Xenova/multilingual-e5-small` is already present under
`<transformers-package-dir>/.cache/Xenova/<model>/` **without importing
`@huggingface/transformers` or triggering any network call**. If it isn't
cached, `--embedder real` fails fast with `code: 'embedder_not_cached'`
rather than silently downloading ~100MB. Pre-cache the model (run any
Lore path that uses the real local embedder once) or use `--embedder fake`
for iteration.

One resolution gotcha worth knowing if you touch this file:
`@huggingface/transformers`'s `package.json` declares a strict `exports`
map that does **not** list `./package.json` as a subpath, so
`require.resolve('@huggingface/transformers/package.json')` throws
`ERR_PACKAGE_PATH_NOT_EXPORTED` — it does not "not find" the package, it
finds it and then Node refuses the subpath. The fix used here is to resolve
the package's actual entry point (`require.resolve('@huggingface/transformers')`)
and walk up from there to the nearest `package.json` whose `name` field
matches.

## Metrics computed

All computed by `runner.mjs`'s `aggregateMetrics()`, against exact-id
scoring vs. `questions.json`'s `expectedIds`:

- **hit@1 / hit@3 / MRR**, separately for `terse` and `chatty` phrasing of
  each question, at `--max` (default 10).
- **terse/chatty top-3 agreement** — mean Jaccard of the top-3 result-id
  sets between the terse and chatty phrasing of the same question, plus the
  % where the two top-3 sets are exactly equal. Low agreement with high
  hit@1 on both individually means phrasing shifts *which* neighbors show
  up even when the top hit is stable — that's D3 territory, not a bug by
  itself.
- **prefix stability** — % of questions where the top-10 result (at
  `--max 10`) is identical, in order, to the first 10 of the top-50 result
  (at `--wide-max 50`) for the *same* query. If these differ, widening the
  result window changed the ranking of the first 10, which is a stronger
  and more concerning signal than agreement between two phrasings.
- **mean pairwise Jaccard of top-10** across all `24×23/2` distinct question
  pairs — a baseline "how much do unrelated questions' result sets overlap
  by default" number. D3 should compare a regression's value against this
  baseline, not an absolute threshold.
- **gibberish zero-hit rate** — how often the 60 no-overlap gibberish
  queries return zero results. Note: `RecallHit` has no per-hit score field
  (ranking is array order only, per `packages/lore/src/index.ts`'s
  `RecallHit` type), so "hit" here only distinguishes empty vs. non-empty
  result sets — it is **not** a precision/recall measure against the
  gibberish queries. Semantic search over embeddings essentially never
  returns literally zero hits (there is always a nearest neighbor); expect
  this to read low or 0% even when the harness is working correctly. The
  meaningful signal for gibberish is the score-quantile comparison below.
- **real vs. gibberish `top_score` quantiles** — `RecallMeta.top_score`
  (and `.confidence`) are the only per-*query* (not per-hit) calibration
  signals Lore exposes; this is the actual input D1 needs. Quantiles
  (`p0/p10/p25/p50/p75/p90/p100`) are reported separately for the 24 real
  questions and the 60 gibberish queries. **D1's calibration/abstention
  design should be read directly off the gap (or lack of one) between the
  gibberish p90/p100 and the real p0/p10** — if gibberish queries routinely
  score as high as real ones, a fixed `top_score` threshold can't
  distinguish "answerable" from "nonsense," which is exactly the
  calibration problem D1 is scoping.

## Fixed baseline

`baseline/sqlite-real-10k.json` (+ matching `.md`) is the committed
reference run: `--engine sqlite --embedder real --code-rows 10000 --depth 0
--search-mode hybrid`, main @ v3.21.0. Treat it as the number to diff
against, not a target to re-derive by hand — re-run the harness with the
same flags if you need to reproduce it locally (the fixture is fully
deterministic; only wall-clock timings will differ).

## Design choices worth knowing before extending this harness

- **`depth: 0` is deliberate**, not a placeholder — see above. Don't "fix"
  it to the `recall()` default without checking with D4 first.
- **`bulkIngest`'s sync-embed path calls `embedDocumentBatch` on the
  injected `EmbeddingProvider` unconditionally**, even though the type
  declares it optional (`packages/lore/src/providers/types.ts`) — any
  custom provider used with this harness must implement it.
- **Both the fixture-build `createLore()` call and the eval-phase
  `createLore()` call must use the exact same embedder configuration.**
  Mismatched embedders (e.g. building with `fake` and evaluating with the
  default real provider) fail loudly with a `[VerbatimStore] Embedding
  model fingerprint mismatch` error rather than silently producing garbage
  numbers — if you see that error, check that both `createLore()` call
  sites in `lib/buildFixture.mjs` and `runner.mjs` agree.
- **Never let a real-embedder run trigger a download.** The cache check is
  intentionally fail-closed (`embedder_not_cached`, no fallback to
  downloading) — if you need the model cached in a fresh environment,
  that's a separate, explicit step, not something this harness should do
  for you.
